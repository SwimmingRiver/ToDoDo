# 반복 종료 설정 UI 설계

작성일: 2026-11-05
대상: 웹(`client`), 앱(`mobile`), 공통 로직(`packages/core`)

## 1. 왜 하는가

지금은 반복의 종료 조건을 사용자가 직접 고르지 않는다. 폼의 「만료일시(마감일시)」에서 자동으로 정해진다(`toRecurrenceRule`).

- 마감일이 있으면 그 날짜까지 반복(`untilDate`)하고, 없으면 무기한(`indefinite`)으로 반복한다.
- 반복을 켜면 이 칸은 사실상 마감 역할을 하지 않는다. 회차의 시각은 「시작일시」에서 오고, 각 회차는 `startAt = dueAt = 그날 시작 시각`으로 저장된다(`buildRecurringOccurrenceDoc`). 결국 이 칸은 "시리즈 종료일"로만 쓰인다.

이 때문에 실제로 생긴 문제(2026-11-05 사용자 시뮬레이터 테스트):

1. **무기한 반복을 만들 방법이 안 보인다.** 마감일을 지워야 하는데, 지우기 ✕ 버튼이 16px 연회색이라 사용자가 찾지 못했다.
2. **오늘·캘린더 탭에서 추가하면 거의 항상 잘린 시리즈가 된다.** 「+ 할 일 추가」가 선택한 날짜를 마감일에 자동으로 채운다(`TodayScreen.tsx:45`, `CalendarScreen.tsx:84`). 이 상태로 반복을 켜면 그날 끝나는 시리즈가 된다.
3. **이미 만든 시리즈의 종료일을 바꿀 수 없다.** 수정 시에는 기존 종료 조건을 그대로 유지한다(`toRecurrenceRuleForEdit`, #160). 반복 후속 목록 3번(B안)이 이것이다.
4. **이미 지난 종료일 시리즈를 수정하면 "생성 가능 기간 벗어남" 오류가 난다.** 반복 후속 목록 4번이다.

선행 작업: 종료일이 4주 호라이즌보다 먼 시리즈가 4주에서 멈추던 버그는 #168로 고쳤다(develop 병합). 그래서 먼 종료일도 안전하게 고를 수 있다.

## 2. 목표 / 비목표 / 실패 조건

**목표**
- 반복을 켜면 반복 섹션 안에서 「종료: 없음 / 날짜 지정」을 직접 고른다. 새로 켤 때 기본값은 「없음」이다.
- 이미 반복 중인 시리즈도 같은 컨트롤로 종료 조건을 바꿀 수 있다(없음 ↔ 날짜, 날짜 변경).
- 웹과 앱이 같은 규칙으로 동작한다. 규칙은 core에 한 곳만 둔다.

**비목표**
- "N회 후 종료" 옵션은 넣지 않는다.
- 데이터 모델을 바꾸지 않는다. `RecurrenceRule.endType`/`endDate`가 이미 있어 마이그레이션도 필요 없다.
- 기존 시리즈를 수정할 때의 「만료일시」 칸 동작은 바꾸지 않는다(4-3 참고).
- 반복을 끈 옛 시리즈 데이터 정리(후속 5번)는 이 작업에 넣지 않는다.

**실패 조건 (기술적으로 돌아가도 실패로 본다)**
- 오늘·캘린더 탭에서 추가한 반복이 여전히 그날로 잘린다.
- 종료일을 줄였을 때 수정 중이던 회차나 완료한 회차가 사라진다.
- 기존 시리즈의 제목만 고쳐 저장했는데 종료 조건이 바뀐다(#160 회귀).

## 3. 사용자에게 보이는 동작

### 3-1. 반복 섹션 (웹 `recurrenceFields.tsx`, 앱 `RecurrenceSection.tsx`)

기존 "반복 범위" 안내 블록을 「반복 종료」 컨트롤로 바꾼다.

- 라벨: **반복 종료**
- 두 가지 중 하나를 고른다. 웹은 기존 `RecurrenceTypeTabs`처럼 탭이나 라디오, 앱은 기존 주기 칩과 같은 라디오 칩.
  - **없음**: 계속 반복된다.
  - **날짜 지정**: 고르면 날짜 입력이 나타난다. 날짜만 받고 시각은 받지 않는다. 웹은 `<input type="date">`, 앱은 날짜만 고르는 피커.
- 안내 문구(현재 `rangeText` 대체)
  - 없음: "계속 반복됩니다"
  - 날짜 지정, 날짜 있음: "YYYY-MM-DD까지 반복됩니다"
  - 날짜 지정, 날짜 없음: 검증 오류로 표시(3-3)
- 「날짜 지정」을 처음 고를 때 날짜 칸의 초기값: **빈 칸**. 시작일 + 1개월 같은 추측 값을 넣지 않는다. *(내 판단)*

### 3-2. 새로 반복을 거는 경우 (생성 폼, 일반 할 일 → 반복 전환)

- 반복을 켜면 종료는 항상 **「없음」**으로 시작한다. 이미 입력돼 있던 「만료일시」를 종료일로 옮기지 않는다. *(내 판단. 앞서 대화에서는 옮기는 안을 말했지만, 그러면 오늘·캘린더 탭이 자동으로 채운 날짜가 그대로 종료일이 되어 문제 2가 다시 생긴다.)*
- 반복이 켜져 있는 동안 「만료일시」 칸을 **숨긴다**. 이 칸은 반복 회차에 쓰이지 않기 때문이다.
  - 숨긴 값은 검증하지 않는다(`getTodoDateValidationError`의 dueAt 검사 제외). 그러지 않으면 자동으로 채운 마감일(그날 00:00)이 시작일시보다 앞서 보이지 않는 오류가 난다.
  - 숨긴 값은 반복 규칙 계산에 쓰지 않는다. 생성 시 회차의 dueAt은 어차피 `buildRecurringOccurrenceDoc`이 덮어쓴다.
  - 반복을 다시 끄면 칸이 원래 값 그대로 다시 나타난다(상태는 지우지 않는다).
- **마감 알림 선택칸**: 지금은 마감일이 없으면 비활성인데, 반복 회차에는 각각 마감 시각(= 시작 시각)이 있다. 그래서 반복이 켜져 있으면 시작일시를 기준으로 활성화하고, `reminderOffsetMinutes`도 dueAt과 무관하게 저장한다. 알림 권한 안내(`offerIfDue`)도 시작일시 기준으로 띄운다. *(내 판단)*

### 3-3. 검증 (core `getRecurrenceValidationError`)

- 매주 반복에 요일이 없으면 오류(기존 유지).
- 「날짜 지정」인데 날짜가 비어 있으면 **"종료일을 선택해주세요"**.
- 종료일이 시작일시의 날짜보다 앞서면 **"종료일은 시작일과 같거나 이후여야 합니다"**. 비교는 로컬 날짜 키 기준(기존 `toLocalDateKey` 방식).
- 생성과 수정 모두 같은 검증을 적용한다. 수정 때 범위 오류를 숨기던 분기(`existingRule ? (null, null)`)는 없앤다. 수정 폼의 시작일시는 그 회차의 날짜이므로 "이 회차보다 앞선 종료일 금지"라는 뜻이 된다.
- 종료일 상한은 두지 않는다. #168 이후 먼 종료일도 연장 작업이 이어 채운다.

### 3-4. 기존 시리즈 수정 (웹 `todoForm`(수정)·`todoDetail`, 앱 `TodoDetailScreen`)

- 반복 섹션은 기존 규칙의 종료 조건으로 채워진다(`toFormValue`가 endType/endDate까지 옮긴다).
- 종료를 바꾸고 저장하면 기존 시리즈 수정 흐름을 그대로 탄다. 확인 창 「이 일정과 이후 일정」을 거쳐 `editRecurringSeries`를 호출한다. 확인 창 문구는 바꾸지 않는다. *(내 판단: 종료일을 줄이면 미래 회차가 줄어든다는 사실은 "이후 일정이 새 설정으로 바뀐다"는 기존 문구 범위 안이다.)*
- 「만료일시」 칸은 지금처럼 보인다(그 회차의 날짜). 숨기지 않는 이유: 숨긴 지난 회차의 마감을 미래로 옮겨 다시 보이게 하는 경로(#167)가 이 칸을 쓴다.
- 제목만 고쳐 저장하면 폼의 종료 값이 기존 규칙과 같으므로 종료 조건이 바뀌지 않는다(#160의 보장을 폼 값으로 유지).

## 4. core 변경

### 4-1. 폼 값 타입 (`packages/core/src/recurring/recurrenceForm.ts`)

```ts
export interface RecurrenceFormValue {
  type: "daily" | "weekly" | "monthly";
  weekdays?: number[];
  endType: "indefinite" | "untilDate";
  /** "YYYY-MM-DD". endType === "untilDate"일 때만 의미가 있다. */
  endDate: string | null;
}
```

- `toFormValue(rule)`: endType/endDate도 옮긴다. 옛 문서처럼 endType이 없거나 이상한 값이면 `indefinite`로 둔다. endDate가 `YYYY-MM-DD`가 아니면 `null`로 둔다.
- `toRecurrenceRule(value)`: 인자에서 dueAt을 뺀다. 폼 값의 endType/endDate를 그대로 규칙으로 만든다. `indefinite`면 `endDate: null`. Firestore `undefined` 금지 규칙(키 생략)은 유지한다.
- `toRecurrenceRuleForEdit`: 폼 값이 종료 조건을 담게 되어 필요 없어진다. 삭제하고 호출부 4곳(웹 `todoForm`·`todoDetail`, 앱 `TodoDetailScreen`, 그 외 grep 결과)을 `toRecurrenceRule`로 바꾼다.
- 반복을 새로 켤 때의 기본 폼 값(`{ type: "daily", endType: "indefinite", endDate: null }`)을 core에 상수나 함수로 두고 웹·앱이 함께 쓴다. *(내 판단)*

### 4-2. 검증 (`getRecurrenceValidationError`)

- 시그니처를 `(value, startAt)`으로 바꾼다. dueAt 인자를 없애고 3-3 규칙을 적용한다.
- 웹은 `client/src/features/todo/components/recurrence/recurrenceValidation.ts`로 core를 다시 내보낸다. 문구 상수(`WEEKDAY_REQUIRED_ERROR` 등)처럼 종료 오류 문구도 core에서 내보낸다.

### 4-3. 시리즈 수정의 "0개 생성" 처리 (`seriesApi.ts` `editRecurringSeriesImpl`)

지금은 다시 만들 회차가 0개면 무조건 "생성 가능 기간 벗어남"으로 실패한다(후속 4번의 원인). 종료일을 고를 수 있게 되면 0개가 정상인 경우가 생긴다. 예를 들어 지난 회차를 열어 종료일을 어제로 두면 이후 회차가 없는 게 맞다.

- **바꿀 규칙**: 0개일 때 실패하는 것은 **시작일시가 호라이즌 밖이라 만들 수 없는 경우**(기존 데이터 손실 방지 목적, 9f659ea)로 한정한다. 그 밖의 0개(종료일이 재생성 창보다 앞서거나, 창 안에 해당 요일이 없음)는 정상 저장한다. 창 안의 todo 회차는 지워지고 새로 만들어지지 않는다.
- 생성(`createRecurringTodoImpl`)의 0개 실패는 유지한다. 새 시리즈에서 0개는 검증(종료일 ≥ 시작일)을 통과했다면 호라이즌 밖 시작이라는 뜻이기 때문이다.
- 회귀 테스트(core): 지난 종료일 시리즈의 지난 회차 제목 수정이 성공해야 한다(후속 4번). 종료일을 줄이면 새 종료일 이후의 todo 회차만 지워지고 done/doing 회차는 남아야 한다. 시작일시가 호라이즌 밖이면 여전히 실패하고 기존 회차를 보존해야 한다.

## 5. 앱 날짜 입력

`DateTimeField`는 날짜와 시각을 함께 받는다. 종료일은 날짜만 필요하다.

- `DateTimeField`에 날짜만 받는 모드를 추가하거나 날짜 전용 필드를 새로 만든다. *(방식은 구현자 판단)*
- 값은 `YYYY-MM-DD` 로컬 날짜 키로 주고받는다. 로컬 자정을 `toISOString()`으로 바꿔 날짜를 자르는 방식은 금지한다([[dueat-utc-storage]] 함정). `toDateKeyFromISO` 같은 기존 유틸을 쓴다.
- 터치 영역은 44pt 이상(`MIN_TOUCH_TARGET`).

## 6. 테스트

- core: `toFormValue`/`toRecurrenceRule` 왕복, 옛 문서(endType 없음·ISO endDate) 정규화, 검증 3종, 4-3의 0개 규칙. 날짜 키를 단언하는 테스트는 로컬 생성자로 픽스처를 만들고 `TZ=America/New_York`에서도 돌린다(11-05 재발 함정).
- 웹: 반복을 켜면 만료일시 숨김, 종료 기본 「없음」, 「날짜 지정」 시 날짜 칸 표시와 빈 값 오류, 오늘 자동 채움 dueAt이 있어도 무기한 시리즈 생성 payload, 기존 시리즈 제목만 수정 시 endType 유지, 종료일 변경 시 `editRecurringSeries` payload에 새 endDate 반영.
- 앱: 웹과 같은 시나리오를 `TodoFormScreen`·`TodoDetailScreen`·`RecurrenceSection` 테스트로. 오늘·캘린더 탭에서 `dueAt` 파라미터를 받아 들어와도 무기한으로 생성되는지.
- 시뮬레이터 실기: 오늘 탭 → 추가 → 반복 켜기 → 저장 → Firestore 회차가 호라이즌(4주)까지 생기고 `endType: indefinite`인지. 기존 시리즈 종료일을 줄였다 늘렸다 하기.
- CI 등가: 웹 vitest는 `VITE_FIREBASE_API_KEY=` 비움, 서울·뉴욕 TZ 둘 다. core dist 재빌드 후 `git diff --exit-code -- dist`.

## 7. 구현자에게 맡기는 것

- 웹의 「없음 / 날짜 지정」 컨트롤 형태(탭/라디오)와 스타일. 기존 반복 섹션 스타일 토큰과 다크모드 토큰을 따른다.
- 앱 날짜 전용 입력의 구현 방식(5절).
- 기본 폼 값 상수의 이름과 위치(4-1).
- 반복 요약 배지·문구 중 종료 조건을 보여 주는 곳이 있으면 새 문구("계속 반복됩니다")와 맞춘다. 2026-11-05 기준 `mobile/src/shared/utils/recurrenceSummary.ts`는 endType을 쓰지 않는다.
- 웹 설계 메모 `client/src/features/todo/design/recurringTodo.spec.md`와 웹 `recurrenceTransform.ts`도 종료 조건을 dueAt에서 유도한다고 적혀 있거나 그렇게 동작하면 맞춰 고친다.

## 8. 내가 정한 것 (사용자 확인 필요)

1. 새로 반복을 켤 때 기존 만료일시를 종료일로 옮기지 않음(3-2).
2. 「날짜 지정」의 초기 날짜는 빈 칸(3-1).
3. 반복이 켜져 있으면 마감 알림을 시작일시 기준으로 활성화(3-2).
4. 기존 시리즈 수정에서는 만료일시 칸을 그대로 둠(3-4).
5. 종료 변경 시 확인 창 문구는 바꾸지 않음(3-4).
6. 시리즈 수정에서 "0개 생성"을 호라이즌 밖 시작일 때만 실패로 봄(4-3).
