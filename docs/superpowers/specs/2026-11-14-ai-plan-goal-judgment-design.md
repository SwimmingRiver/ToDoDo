# AI 플랜 "목표 아님" 판단 설계

작성일: 2026-11-14 · 관련: `docs/superpowers/specs/2026-11-13-ai-plan-guard-design.md`(비용 가드, PR #174)

## 왜 하는가

운영에서 "ㅋㅋ"를 넣으면 Claude가 "목표를 구체적으로 정의하기" 같은 쓸모없는 계획을 만들어 준다. 비용은 #174의 시도 상한(하루 40회)이 이미 막고 있으므로, 이번 작업은 **장난 입력과 목표가 아닌 입력에 계획 대신 안내를 보여 주는 UX 작업**이다. 부수 효과로 장난 입력 한 번의 비용도 줄인다.

#174에서는 "자모 통과"와 "모델 판단 안 함"으로 결정했다. 운영에서 실제 결과를 보고 사용자가 두 결정을 모두 뒤집었다(11-14).

## 목표

1. **규칙 필터 확장**: 글자가 있어도 **모두 한글 자음·모음이면**("ㅋㅋ", "ㅎㅎㅎ", "ㅠㅠ 123") Claude를 부르지 않고 `NOT_A_GOAL`을 돌려준다.
2. **모델 판단**: 규칙을 통과한 입력은 Claude가 계획을 만들면서 "이 입력에서 해 볼 만한 일을 끌어낼 수 있나"를 함께 판단한다. 아니면 계획 대신 `NOT_A_GOAL`을 돌려준다.
3. 거절될 때 모델 출력이 짧아서(계획을 만들지 않으므로) 호출 비용이 작다.
4. 웹은 기존 `NOT_A_GOAL` 안내를 쓰고, 문구만 넓은 의미에 맞게 다듬는다.

## 판단 기준 (사용자 결정)

기준은 문장 형태가 아니라 **넉넉하게 읽어도 할 일로 쪼갤 만한 것이 있는가**다.

- **통과**
  - 질문 형태의 목표: "토익 800점 받으려면 어떻게 해야 해?", "한 달 안에 5kg 뺄 수 있을까?", "이사 준비 뭐부터 하지"
  - 막연한 상태: "심심해", "요즘 너무 무기력해" → 작은 루틴 같은 계획
  - 짧은 명사형 목표: "운동", "독서"
- **거절**
  - 잡담이나 정보 질문: "날씨 어때", "너 누구야", "1+1은?"
  - 의미 없는 입력: "asdf", "ㅁㄴㅇㄹ"(규칙 필터가 먼저 거름)
- **애매하면 통과시킨다.** 정상 사용자를 막는 쪽이 더 나쁜 실패다.
- 의문문 여부로 거르는 규칙은 쓰지 않는다(사용자와 논의 후 기각). 질문 형태의 목표가 많고, 한국어는 물음표 없는 질문도 흔하다.

## 횟수 처리 (사용자 결정)

| 경로 | 시도(40) | 성공(20) |
| --- | --- | --- |
| 규칙 필터 거절(글자 없음, 자모만) | 안 셈 | 안 셈 |
| 모델이 "목표 아님"으로 판단 | 셈(Claude 호출함) | **안 셈** |
| 계획 생성 성공 | 셈 | 셈 |

이유: 장난을 반복하는 사람은 남은 횟수에 신경 쓰지 않으므로, 성공 횟수를 차감해도 억제 효과가 없다. 차감하면 손해를 보는 건 모델 오판으로 거절된 정상 사용자다. 장난에 대한 실질적인 상한은 시도 40회다.

## 실패로 보는 것 (anti-goals)

- 정상 목표가 모델 판단으로 거절되는 경우. 특히 질문 형태, 짧은 명사형, 막연한 상태 입력.
- 자모 규칙이 정상 입력을 막는 경우. 예: "ㅋㅋ 토익 공부"처럼 완성 글자가 하나라도 섞이면 통과해야 한다.
- 거절 응답에 계획 일부가 섞여 사용자에게 보이는 경우.
- `usage` 표시(성공 n/20)의 의미가 바뀌는 경우.

## 동작

### 요청 처리 순서 (`handlers/plan.ts`)

#174의 순서는 그대로 둔다. 바뀌는 곳은 두 군데다.

```
… → 입력 검증 → 규칙 필터(글자 없음 | 자모만 → 400 NOT_A_GOAL)
→ 성공 한도 → 시도 상한 → 연타 제한 → 시도 +1
→ Claude 호출 → [모델이 목표 아님 → 400 NOT_A_GOAL, 성공 안 셈]
→ 사후 검증 → 성공 +1
```

### 1. 규칙 필터 확장 (`validateInput.ts`의 `isNotAGoal`)

- 기존: trim한 문자열에 `\p{L}`이 하나도 없으면 거절.
- 추가: `\p{L}`에 해당하는 문자가 **모두 한글 자모**이면 거절. 자모 범위는 호환 자모 U+3131–U+318E와 첫가끝 자모 U+1100–U+11FF.
- 라틴 문자 등 다른 글자는 이 규칙에서 판단하지 않는다("asdf"는 모델이 판단).
- *(/code-review 반영)* 판별 전에 NFC로 정규화한다. NFD로 붙여 넣은 정상 한글이 첫가끝 자모로 오판되지 않게 하기 위해서다. 자모 범위에 확장 A·B(U+A960–U+A97F, U+D7B0–U+D7FF)와 반각(U+FFA0–U+FFDC)도 포함한다.
- *(/code-review 반영)* 모델 거절 시 오판 감시용 로그를 남긴다(목표 문장은 제외하고 길이만).

### 2. 모델 판단

- **스키마**(`planSchema.ts`): 최상위 첫 필드로 불리언(예: `isGoal`)을 추가한다. 첫 필드로 두는 이유는 모델이 계획을 쓰기 전에 판단을 먼저 내리게 하기 위해서다. structured outputs는 필드를 정의 순서대로 생성한다.
- **프롬프트**(`prompt.ts`): 위 판단 기준을 규칙으로 추가한다. 통과와 거절 예시를 몇 개 넣고, "애매하면 true", "false면 title은 빈 문자열, items는 빈 배열"을 명시한다.
- **핸들러**: 판단 값이 false이면 `400 { error: "NOT_A_GOAL" }`을 돌려준다. `sanitizePlan`으로 넘기지 않고, 성공 횟수도 올리지 않는다. 판단 값이 true인데 계획이 비어 있으면 기존대로 `PLAN_INVALID`(502)다.
- 판단 값은 서버 안에서만 쓰고 클라이언트 응답의 `plan` 형태는 바꾸지 않는다.

### 3. 웹 (client)

- `aiPlanErrorMessage.ts`의 `NOT_A_GOAL` 문구를 다듬는다. 지금 문구("목표를 글로 적어 주세요")는 기호나 숫자만 있는 경우를 전제로 한다. 초안(빌더가 다듬어도 됨): "이루고 싶은 목표를 적어 주세요" / "예: 다음 달까지 토익 800점 받기".
- 안내는 기존처럼 토스트로 뜬다. 토스트가 모달 뒤에 깔리던 문제는 PR #177로 해결했다(모달보다 z-index가 높음).
- 새 코드는 추가하지 않는다. 구버전 웹도 `NOT_A_GOAL`을 이미 알고 있다.

### 4. 오판 검증

- 통과 15개, 거절 10개 정도의 입력 목록을 만든다(위 판단 기준의 예시 포함).
- 운영과 같은 모델(Haiku 4.5)로 한 번 실행해 판단 결과를 표로 남긴다. **실제 API 비용이 들므로 실행 전에 사용자 승인을 받는다.** 예상 비용은 수십 센트 이하다.
- 통과 목록에서 하나라도 거절되면 프롬프트를 고치고 다시 실행한다. 거절 목록 중 일부가 통과하는 건 허용한다("애매하면 통과").
- 검증 스크립트는 리포지토리에 커밋하지 않아도 된다. 결과 표는 PR 본문에 붙인다.

### 배포

- Worker만 바뀌면 기능이 동작한다(웹 문구는 개선일 뿐이다). 배포 순서는 상관없다.
- 새 바인딩이나 환경변수는 없다.
- *(빌더 확인 후 정함)* PR #177(토스트 z-index)과 코드가 겹치지 않으므로 이 작업은 origin/develop에서 바로 시작한다. #177이 먼저 병합되면 운영에서 안내 토스트가 모달 위에 보인다. 웹 화면 확인은 두 PR이 모두 develop에 들어간 뒤에 한다.

## 테스트

- 규칙 필터: "ㅋㅋ", "ㅎㅎㅎ", "ㅠㅠ 123", "ㅋ" → 거절. "ㅋㅋ 토익 공부", "토익 800", "asdf", "운동 🏃" → 통과.
- 핸들러: 가짜 클라이언트가 판단 값 false를 돌려주면 400 `NOT_A_GOAL`, 시도는 +1, 성공은 그대로. 판단 값 true인 기존 성공과 실패 경로는 그대로.
- 프롬프트: 판단 기준 문구가 들어 있는지 정도만 확인한다(실제 판단 품질은 4번 검증이 맡는다).
- 클라이언트: `aiPlanErrorMessage` 문구 테스트.

## 하지 않는 것

- 판단 결과를 사용자별로 기록하거나 통계를 내는 것.
- 모바일 앱 변경(AI 플랜 없음).
- 의문문 규칙, 길이 규칙, 금칙어.

## 빌더에게 맡기는 것

- 판단 필드 이름, 프롬프트 문구와 예시 선정.
- 자모 판별 함수의 구현 방식(정규식 범위 등).
- 오판 검증 입력 목록의 세부 구성.
