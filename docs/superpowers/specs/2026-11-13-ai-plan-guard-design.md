# AI 플랜 비용 가드 설계

작성일: 2026-11-13 · 브랜치 `feat/ai-plan-guard` · 관련: `docs/superpowers/specs/2026-09-25-ai-plan-design.md`

## 왜 하는가

결제(`VITE_BILLING_ENABLED`)를 열기 전에 **AI 플랜의 계정당 비용에 끝이 있게** 만든다. 걱정하는 상황은 UX보다는 누군가 일부러 토큰을 태우는 경우다.

현재 `ai-proxy/src/handlers/plan.ts`는 성공했을 때만 하루 20회 카운트를 올린다. 실패 경로는 502(`PLAN_INVALID`: 거절·`max_tokens`·파싱 실패)와 503(`AI_UNAVAILABLE`)이고, 둘 다 차감되지 않는다. 그래서 거절을 유발하는 입력을 반복하면 호출마다 최대 4096 출력 토큰을 한도 없이 쓸 수 있다. 같은 파일 주석에 "결제로 공개 전 반드시 닫아야 한다"고 적혀 있는 기존 한계다.

비용 규모: 모델은 Haiku 4.5(출력 $5/MTok)이고, 최악의 경우 호출 1회에 약 $0.02가 든다. 시도 상한을 40회로 두면 계정당 하루 최대 약 $0.8이다.

## 목표

1. **시도 상한**: Claude까지 도달한 요청은 결과와 상관없이 하루 단위로 센다. 상한을 넘으면 Claude를 호출하지 않는다.
2. **규칙 필터**: 글자가 하나도 없는 입력은 Claude에 보내지 않는다.
3. **연타 제한**: 같은 계정이 짧은 시간에 요청을 몰아치는 것을 막는다.
4. 웹에서 새 오류마다 알맞은 안내 문구를 보여 준다.

## 하지 않는 것 (사용자 결정)

- **"날씨 어때"처럼 무관한 입력을 모델로 판별하지 않는다**(`actionable` 스키마 필드 등). 비용은 시도 상한이 막으므로 이 기능은 순수한 UX 문제이고, 프롬프트 변경과 오판 검증까지 붙어 범위가 커진다. 이번에는 뺀다.
- **같은 글자 반복("ㅋㅋㅋ", "aaaa")은 필터하지 않는다.** 정상 입력과 섞이면 판별이 애매하다. 자음·모음만 있는 입력도 글자로 쳐서 통과시킨다.
- **탈퇴 후 재가입으로 체험을 다시 받는 문제는 별도 작업으로 미룬다.** 탈퇴 후에도 식별자를 보관하려면 개인정보처리방침 3판과 시행 7일 전 공지가 필요하다.
- 별도 분류 모델 호출, 금칙어 필터, 기기 지문, 체험에 카드 요구.
- 모바일 앱 변경: 앱에는 AI 플랜이 아직 없다.

## 실패로 보는 것 (anti-goals)

- 정상 목표("다음 달까지 토익 800점")가 규칙 필터에 막히는 경우.
- 시도 상한이 기존 하루 20회(성공 기준) 한도의 의미나 표시를 바꾸는 경우. 클라이언트에 보이는 `usage: { used, limit }`는 지금처럼 성공 횟수다.
- 연타 제한이 정상 흐름(결과를 받은 직후 "다시 만들기", 실패 후 재시도)을 막는 경우.
- 우리 쪽 장애나 설정 누락(예: 바인딩 없음) 때문에 모든 요청이 막히는 경우.

## 동작

### 요청 처리 순서 (`handlers/plan.ts`)

```
인증(401) → 프리미엄(403) → 입력 검증(400 INVALID_INPUT)
→ 규칙 필터(400 NOT_A_GOAL)
→ 성공 20회 한도(429 DAILY_LIMIT)
→ 시도 상한(429 ATTEMPT_LIMIT)
→ 연타 제한(429 TOO_FREQUENT) → 시도 카운트 +1(쓰기 실패 시 429 TOO_FREQUENT)
→ Claude 호출 → 사후 검증 → 성공 카운트 +1
```

**[11-13 리뷰 반영]** 처음에는 연타 제한을 하루 한도보다 앞에 뒀다. 그런데 그러면 한도를 다 쓴 사용자가 몇 번 누르면 "오늘 다 썼어요" 대신 TOO_FREQUENT를 보게 된다. 그래서 연타 제한을 하루 한도 뒤, 시도 +1 바로 앞으로 옮겨 Claude까지 갈 요청만 슬롯을 쓰게 했다. KV 읽기 비용은 작아서 감수한다. 시도 카운터 쓰기가 실패하면 Claude를 부르지 않고 TOO_FREQUENT로 돌려준다. KV는 같은 키에 초당 1회 쓰기 제한이 있어 1초 안에 두 요청이 오면 실패할 수 있는데, 이때 통과시키면 세지 못한 호출로 상한이 우회된다.

### 1. 규칙 필터

- 조건: trim한 goal에 유니코드 문자(`\p{L}`)가 **하나도 없으면** 거절한다. 숫자, 이모지, 문장부호, 공백만으로 된 입력이 여기에 해당한다. 한글 자모(ㅋ, ㅎ)는 `\p{L}`이라 통과한다.
- 응답: `400 { error: "NOT_A_GOAL" }`. 어떤 카운트도 올리지 않는다.
- 위치: `validateInput.ts` 근처에 순수 함수로 둔다. 기존 `INVALID_INPUT`과 구분되는 코드여야 클라이언트가 다른 문구를 보여 줄 수 있다.

### 2. 연타 제한

- 정책: uid당 **10초에 3회**(사용자 결정 11-13). 처음에는 1회였지만, 10초 창은 요청을 받은 순간부터 세고 Haiku 응답에는 몇 초가 걸린다. 그래서 1회로 두면 결과를 받자마자 누르는 "다시 만들기"(`aiPlanModal.tsx` `requestRegenerate`)나 실패 후 바로 하는 재시도가 막힌다. 비용 총량은 시도 상한이 막으므로 3회로 완화해도 방어가 약해지지 않는다. 클라이언트에 쿨다운 표시는 넣지 않는다.
- 구현: **Cloudflare Workers Rate Limiting 바인딩**(`[[ratelimits]]`, `limit: 3`, `period: 10`, key = uid)을 쓴다. KV는 `expirationTtl`이 최소 60초이고 반영이 늦어서 10초 간격을 판정하기에 맞지 않는다. 이 바인딩은 colo별 근사치지만 목적(몰아치기 차단)에는 충분하다.
- 응답: `429 { error: "TOO_FREQUENT" }`.
- 바인딩 호출이 실패하면(예외) **통과시킨다(fail-open)**. 비용의 최종 방어는 시도 상한이 맡기 때문이다.
- *(빌더 확인 필요)* 현재 wrangler `~4.100.0`에서 `[[ratelimits]]`를 지원하는지, 로컬 `wrangler dev`와 테스트에서 어떻게 대체하는지 계획 단계에서 실측한다. 지원하지 않으면 계획에서 대안을 제시하고 사용자 확인을 받는다.

### 3. 시도 상한

- 정책: uid당 서울 날짜 기준 **하루 40회**. 환경변수 `DAILY_ATTEMPT_LIMIT`(기본값 40)로 조정하고, 파싱 방식은 기존 `DAILY_LIMIT`와 같다.
- 저장: 같은 KV(`AI_USAGE`)에 키 `attempts:{uid}:{YYYY-MM-DD}`, TTL은 기존 `USAGE_TTL_SECONDS`(2일)를 쓴다. `usage.ts`의 날짜 키와 읽기·증가 패턴을 재사용한다.
- 시점: 상한 확인을 통과하면 **Claude를 호출하기 직전에** +1 한다. 결과를 보고 세면 동시에 들어온 요청들이 상한을 통과해 버린다. 그래서 503(Anthropic 장애)도 시도로 센다. 상한이 넉넉해서 사용자 손해는 작다.
- 응답: `429 { error: "ATTEMPT_LIMIT" }`.
- 알고 감수한 한계: KV는 원자적이지 않아서 정말 동시에 들어온 요청은 상한을 조금 넘길 수 있다. 기존 `incrementUsage`와 같은 한계이고, 연타 제한이 동시성을 크게 줄여 준다.
- `handlers/plan.ts` 상단 주석의 "결제 공개 전 반드시 닫아야 한다" 문단은 해소된 내용으로 고친다.

### 4. 웹 (client)

- `client/src/features/aiPlan/api/aiProxyApi.ts`: `AiPlanErrorCode`와 `KNOWN_CODES`에 `NOT_A_GOAL`, `TOO_FREQUENT`, `ATTEMPT_LIMIT`를 추가한다. 셋 다 정상 흐름이므로 `EXPECTED_CODES`에 넣어 Sentry로 보내지 않는다.
- `client/src/features/aiPlan/utils/aiPlanErrorMessage.ts` 문구 *(초안, 빌더가 다듬어도 됨)*:
  - `NOT_A_GOAL`: "목표를 글로 적어 주세요" / "이루고 싶은 일을 문장으로 적어 주세요"
  - `TOO_FREQUENT`: "잠시 후 다시 시도해 주세요" / "요청이 너무 잦아요. 잠시 후 다시 눌러 주세요"(숫자는 wrangler.toml 설정과 어긋날 수 있어 빼기로 함)
  - `ATTEMPT_LIMIT`: "오늘 시도 횟수를 다 썼어요" / "내일 다시 시도해 주세요"
- 클라이언트에서 미리 필터하는 기능은 넣지 않는다. 서버가 기준이다.

### 배포

- `ai-proxy/wrangler.toml`에 `[[ratelimits]]` 바인딩과 `DAILY_ATTEMPT_LIMIT = "40"`을 추가한다. 새 KV 네임스페이스는 필요 없다.
- Worker를 먼저 배포하고 웹은 그 뒤에 배포한다. 웹이 먼저 나가도 깨지지 않는다(새 코드가 오기 전까지는 기존 동작). Worker가 먼저 나가면 구버전 웹이 새 코드를 일반 오류 문구("잠시 후 다시 시도해 주세요")로 보여 주는데, 이 정도는 감수한다.
- 운영에서 ai-proxy의 지역 배치(placement)가 바뀌지 않는지 확인한다(HKG 지역차단 이력 참고, PR #151).

## 테스트

- 규칙 필터 단위 테스트: 숫자만, 이모지만, 문장부호만, 섞인 경우 → 거절. "ㅋㅋㅋ", "토익 800", "운동 🏃" → 통과.
- 핸들러 테스트: 순서별 응답 코드. 시도 상한 도달 시 Claude가 호출되지 않는지, 502·503 경로에서도 시도가 +1 되는지, 성공 카운트(`usage`)는 성공 시에만 오르는지, 레이트 리미터가 예외를 던지면 통과하는지.
- 클라이언트: `aiPlanErrorMessage`와 에러 코드 파싱 테스트.
- 로컬 실검증은 `reference_ai_proxy_local_testing`의 절차(`.dev.vars` + VITE 오버라이드)를 따른다.

## 빌더에게 맡기는 것

- 규칙 필터 함수와 시도 카운터의 정확한 파일 배치, 이름.
- 문구 다듬기.
- Rate Limiting 바인딩의 타입 선언 방식과 테스트용 가짜 객체.
