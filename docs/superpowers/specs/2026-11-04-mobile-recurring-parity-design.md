# 모바일 반복 할 일 생성·수정 + 앱 진입 정리 작업 (웹 동등화) 설계

- 작성일: 2026-11-04
- 브랜치: `feat/mobile-recurring-parity` (develop 기준)
- 관련 메모: 결정론적 문서 ID(반복 캘린더 중복), 호라이즌 silent fail, done 아카이빙, startupMaintenance 후속, dueAt UTC 저장

## 1. 의도와 이유

사용자가 원하는 것: 운동·공부처럼 **계속하는 습관을 한 번만 등록**해 두고, 이후에는 새로 만들지 않고 **그날 할 일을 바로 체크**하는 것. 이걸 휴대폰에서도 웹과 똑같이 할 수 있어야 한다.

지금 모바일(RN/Expo, `mobile/`)의 상태:

1. 반복 할 일을 **보여주기만** 한다(배지 등). `TodoFormScreen`·`TodoDetailScreen`에서 반복을 설정하거나 고칠 수 없다.
2. 웹이 앱 진입 시 돌리는 정리 작업(`runStartupMaintenance`)이 **없다**. 반복 인스턴스는 4주 호라이즌만큼만 미리 생성되므로, 앱만 쓰는 사용자는 4주 뒤 반복 할 일이 **에러 없이 끊기고**, 완료 항목도 30일 뒤 보관되지 않는다.
3. 모바일 상세 화면에서 반복 할 일을 삭제하면 **그 회차 문서 하나만** 지워진다. 웹은 시리즈 전체(`deleteRecurringSeries`)를 지운다. 즉 현재 앱에서 반복 할 일을 지워도 나머지 회차가 남는다.

로드맵상 지금은 모바일을 웹 수준으로 맞추는 단계이고 다음이 스토어 제출이다. 앱이 누군가의 주 기기가 되기 전에 데이터 규칙이 웹과 같아야 한다.

## 2. 목표 / 비목표 / 실패 기준

**목표**
- 모바일에서 반복 할 일을 만들고, 고치고(반복 켜기/규칙 변경/끄기), 시리즈 단위로 지울 수 있다. 동작 규칙은 웹과 동일.
- 모바일 앱만 써도 반복 할 일이 끊기지 않고, 완료 항목 아카이빙·overdue 아카이빙이 웹과 똑같이 일어난다.
- 반복 시리즈의 Firestore 쓰기 로직과 정리 작업 로직이 `packages/core` **한 곳**에 있고, 웹과 앱이 같은 코드를 쓴다.

**비목표 (이번 범위 밖)**
- 웹의 반복 규칙·편집 3단 분기 동작 자체를 바꾸는 것. 사용자 확인: "지금 방식으로 하면 될 것 같아."
- **반복 할 일의 모바일 로컬 마감 알림 (사용자 확정: "반복은 알림에서 빼자").** 모바일에서 반복 시리즈를 만들거나 고칠 때, 그리고 정리 작업이 호라이즌을 늘릴 때 `scheduleReminder`를 호출하지 않는다. 비반복 → 반복 전환 시 원래 문서에 걸려 있던 알림은 기존 한계(알림 id 미저장, 취소 불가)대로 남는다. 이유는 두 가지다. 4주치 회차가 iOS 예약 알림 한도 64개를 쉽게 넘고, 알림 취소 구조가 없어 시리즈를 수정·삭제해도 예전 알림이 울린다. 이 문제는 알림 취소 구조와 함께 별도 작업으로 다룬다. 웹 서버 푸시(reminder-proxy)는 회차 문서 기준으로 지금처럼 동작한다.
- 모바일 Sentry 도입. 모바일에는 현재 Sentry가 없다(`mobile/package.json`에 의존성 없음).
- 모바일 피드백 수집·게스트 모드(이식 안 하기로 확정), Apple 로그인(가입 전 진행 불가), 사업자 등록·결제.
- 간격 같은 세부 시각 다듬기. 구현 후 시뮬레이터에서 사용자와 함께 맞춘다.
- 크로스 디바이스 동시 실행 레이스(웹·앱이 같은 순간 정리 작업을 도는 경우)를 새로 해결하는 것. 기존 결정론적 문서 ID가 생성 중복을 막고, 나머지는 기존 웹 멀티탭과 같은 수준으로 둔다.

**실패 기준 (기술적으로는 돌아가도 실패)**
- 1단계 리팩터링 후 운영 웹의 반복 생성·편집·삭제·정리 동작이 조금이라도 달라지는 것.
- 모바일이 웹과 다른 규칙으로 반복 문서를 쓰는 것. 예: 다른 문서 ID 규칙, 다른 dueAt 계산, 하위 할 일과 반복의 상호 배제를 무시하는 것.
- 정리 작업 실패가 사용자 화면을 막거나 에러 팝업을 띄우는 것.

## 3. 진행 구조: PR 두 개 (사용자 확정)

1. **PR 1: 웹 반복·정리 로직을 core로 이동.** 동작 변경은 없다. 웹 기존 유닛 테스트와 E2E가 그대로 통과하는 것이 안전 근거다. develop에 병합한다.
2. **PR 2: 모바일 기능.** core 함수를 써서 작성·상세 화면 UI, 시리즈 삭제, 앱 진입 정리 작업을 붙인다.

PR 2는 PR 1 위에 쌓는다. PR 1이 develop에 병합되기 전에 PR 2 작업을 시작해도 되지만, PR 2의 base는 PR 1 병합 후 develop이다.

## 4. PR 1: core로 옮기는 범위 (사용자 확정: B안, "쓰는 함수까지")

`packages/core`로 옮길 것.
- 순수 로직: `client/src/features/todo/utils/recurrence.ts`, `startupMaintenance.ts`, 여기에 필요한 날짜 유틸(`toDateKeyFromISO`, `localDateKeyToISO` 등 실제로 쓰는 것만).
- Firestore 쓰기 함수: `createRecurringTodo`, `editRecurringSeries`, `deleteRecurringSeries`, `runStartupMaintenance`, 그리고 이들이 의존하는 내부 함수(`withRecurringSeriesLock`, `fetchAllUserTodos`, `commitUpdates`/`commitArchiveGroups`/`commitCreates`, `nextRootOrderFrom`, `runSweep`, `assertNoRecurrenceParentConflict` 등).
- 반복 폼의 검증·변환처럼 UI 프레임워크와 무관한 순수 함수(웹 `components/recurrence/recurrenceValidation.ts`, `recurrenceTransform.ts`, `weekdayConstants.ts` 중 비-UI 부분). 모바일 폼이 같은 검증 문구와 같은 변환을 쓰기 위해서다.

core 함수의 형태는 기존 core 관례를 따른다. `db: Firestore`와 `userId`를 인자로 받고, 전역 `db`/`auth`를 import하지 않는다.

웹 전용 의존성 처리
- Sentry: core는 `@sentry/*`를 import하지 않는다. `runStartupMaintenance`가 스윕별 실패를 보고할 콜백(예: `onSweepError(error, sweepName)`)을 인자로 받고, 웹은 거기에 현재와 똑같이 `console.error` + `Sentry.captureException(error, { tags: { sweep } })`을 연결한다.
- 웹 `todoApi.ts`의 기존 export 이름과 시그니처는 그대로 유지한다. 웹 훅·컴포넌트는 손대지 않고, 내부만 core에 위임하는 얇은 래퍼(전역 `db`·현재 uid 주입)로 바꾼다.

**잠금(`withRecurringSeriesLock`) 주의:** 이 잠금은 생성·편집·삭제·정리 작업이 **같은 잠금 하나를 공유**해야 의미가 있다. core 모듈 수준에 단일 인스턴스로 두고, 위 네 함수가 모두 같은 잠금을 거치게 한다.

**테스트:** 순수 로직의 기존 유닛 테스트는 core로 함께 옮긴다. 웹 todoApi 테스트(`recurringTodoApi.test.ts`, `startupMaintenance.api.test.ts` 등)는 `firebase/firestore`와 `@/shared/lib/*`를 `vi.mock`으로 바꿔 끼우고 있어서, 로직이 core로 옮겨지면 mock이 닿지 않을 수 있다. *(내 판단)* 이 테스트들은 **mock 배선과 호출 위치는 고쳐도 된다.** 다만 기대값(어떤 문서가 어떤 필드로 쓰이는지, 어떤 순서로 어떤 에러를 내는지)은 바꾸지 않는다. 실제 Firestore 쓰기 테스트는 core 쪽에서 core 단위 mock으로 다시 쓰고, 웹에는 래퍼가 `db`·uid·Sentry 콜백을 제대로 주입하는지만 확인하는 테스트를 남긴다. 동작이 같다는 최종 증명은 기대값을 유지한 테스트 + 웹 E2E 통과다. 기대값을 바꿔야 하는 테스트가 생기면 그 자체를 동작 변경 신호로 보고 멈춘다. 날짜 테스트는 절대 날짜 하드코딩 대신 시스템 시간 mock으로 고정한다. UTC 리터럴 픽스처가 버그 구현을 통과시키지 않게 로컬 시간 기준으로 검증한다.

**검증:** 웹 유닛 테스트(CI와 같게 `VITE_FIREBASE_API_KEY=` 빈 값으로 실행), core 테스트, 웹 E2E(로컬은 JDK 21 + 8080 포트 고아 에뮬레이터 확인), 웹 빌드·번들 증분 확인.

`startupMaintenanceGate.ts`(uid별 한 번만 실행하는 모듈 가드)는 웹의 페이지 수명 개념이라 core로 옮기지 않는다. 웹에 그대로 둔다.

## 5. PR 2: 모바일

### 5.1 작성 화면 (`TodoFormScreen`): A안 (사용자 선택)

브레인스토밍 시안 A, "스위치 + 펼침", 웹과 같은 구조.
- 만료일시 아래에 "반복" 스위치를 둔다. 켜면 아래에 펼쳐진다.
  - **반복 주기:** 매일 / 매주 / 매월 칩. 기존 `PriorityChips`와 같은 모양.
  - **매주:** 요일 7개 원형 토글. 최소 1개 선택해야 하며, 없으면 웹과 같은 에러 문구.
  - **매월:** "매월 N일에 반복됩니다 (시작일시 기준)". N ≥ 29이면 "31일이 없는 달은 해당 월 마지막 날에 생성됩니다" 보조 문구.
  - **반복 범위:** 만료일시가 있으면 "YYYY-MM-DD까지 반복됩니다", 없으면 "마감일시가 없으면 무기한으로 반복됩니다". 범위 검증 에러도 웹과 같다.
- 시작일시가 비어 있으면 스위치를 끄고 "반복 설정은 시작일시를 입력해야 사용할 수 있습니다"를 표시한다. 반복이 켜진 상태에서 시작일시를 지우면 반복을 끈다(웹과 동일).
- 저장: 반복이 켜져 있으면 core `createRecurringTodo`, 아니면 기존 `createTodo`.
- 문구는 웹과 동일하다. 간격·색 세부는 구현 후 사용자와 시뮬레이터에서 조정한다.

### 5.2 상세 화면 (`TodoDetailScreen`): 고치기

웹 `todoDetail.tsx`의 분기를 그대로 따른다.
- 같은 반복 섹션을 보여 준다. 하위 할 일이 있으면 비활성이고 "하위 할 일이 있는 항목은 반복을 설정할 수 없습니다"를 표시한다.
- **비반복 → 반복:** `createRecurringTodo`로 새 시리즈를 만들고, 성공한 뒤에만 원래 문서를 지운다. 지우기에 실패하면 웹과 같은 안내를 띄운다.
- **반복이던 항목을 수정**: 규칙 변경, 반복 끄기, 그리고 **규칙은 그대로 두고 제목·설명·우선순위·날짜만 고치는 경우까지 모두** 해당한다. 웹 `todoDetail.tsx`는 `todo.recurrence != null`이면 어떤 필드를 고쳐도 이 경로로 보낸다. 지금 모바일은 같은 경우 `updateTodo`로 문서 하나만 고치는데, 이것도 웹 방식으로 바꾼다. 먼저 확인 창(`Alert.alert`, 웹 확인 모달 문구)을 띄운다. 확인하면 `editRecurringSeries`가 끝낸 회차와 진행 중이거나 기한이 지난 회차는 보존하고 미래 회차만 재생성한다.
- 반복 할 일에는 "+ 하위 할 일 추가"를 막는다. 웹과 같은 상호 배제 규칙이고, 지금 모바일은 막지 않는다.
- 저장 중 더블탭 중복 실행을 막는다. 기존 모바일 mutation 가드 패턴을 따른다.

### 5.3 삭제

`recurrenceId`가 있는 할 일을 삭제하면 "반복 일정이 모두 삭제됩니다" 취지의 확인 창(웹 문구)을 띄운 뒤 `deleteRecurringSeries`로 시리즈 전체를 지운다. 상세 화면과 목록 등 모바일에서 삭제가 가능한 모든 진입점에 적용한다. 지금은 단일 삭제만 되는 버그를 고치는 것이다.

### 5.4 체크

오늘 탭 등에서 회차를 체크하는 기존 동작은 바꾸지 않는다.

### 5.5 앱 진입 정리 작업

- 하는 일은 core `runStartupMaintenance`로, 웹과 같은 세 가지다. done 30일 아카이빙, overdue 반복 회차 아카이빙, 무기한 시리즈 4주 호라이즌 연장.
- **언제** (내 제안, 사용자가 "현실적"이라고 동의):
  1. 로그인 직후 또는 앱 콜드 스타트 시 1회.
  2. 앱이 포그라운드로 돌아왔을 때(`AppState` → `active`), 그 사용자의 마지막 성공 실행 후 **24시간 이상** 지났으면 다시 실행.
- 마지막 실행 시각은 기기 로컬에 uid별로 저장한다. 저장소는 모바일에 이미 있는 것을 쓰고, 없으면 builder 판단으로 정한다. 같은 프로세스에서 동시에 두 번 돌지 않게 진행 중 가드도 둔다.
- 쓴 문서가 1개 이상이면 `["todos"]` 쿼리를 무효화한다(웹과 동일).
- 실패: 사용자에게는 조용히 넘어가고 `console.error`로만 남긴다(모바일 Sentry 없음). 실패하면 마지막 실행 시각을 갱신하지 않아 다음 포그라운드 때 다시 시도한다. 마지막 실행 시각은 세 스윕 중 하나라도 실패하면 갱신하지 않는 것을 기본으로 한다. 스윕별 실패를 삼키는 웹 구조상 이를 알려면 `onSweepError` 콜백으로 실패 여부를 수집한다.
- 로그아웃 후 다른 계정으로 로그인하면 그 계정 기준으로 다시 돈다.

### 5.6 모바일 표시

모바일 `collapseRecurringInstances`는 이미 `overdueArchived`를 반영한다. 정리 작업이 쓴 결과가 목록·오늘·캘린더에 웹과 같은 규칙으로 보이는지 확인만 한다(캘린더는 overdueArchived 대상이 아님, 웹과 동일).

### 5.7 테스트·검증

- 폼·상세 화면 반복 섹션의 컴포넌트 테스트(토글, 비활성 사유, 요일 최소 1개, 매월 안내, 범위 안내). `@testing-library/react-native` v14는 render·fireEvent가 async다.
