# App Privacy(개인정보 라벨) 답변 초안

2026-11-26 develop 코드 기준(11-23 초안 + #233 서버 푸시 반영). Apple 기준에서 "수집"은 데이터가 기기를 떠나 운영자 또는 제3자(외부 서비스)가 실시간 처리 이상으로 접근할 수 있는 경우를 말한다. 기기 안에만 있는 데이터(AsyncStorage)는 라벨 대상이 아니다.

## 추적(ATT)

**추적하지 않음 → "아니요"**. 근거는 다음과 같다.
- 광고 SDK와 IDFA 접근이 없다.
- Firebase Analytics를 초기화하지 않는다. `mobile/src/firebase/index.native.ts`는 `initializeApp`과 `initializeAuth`만 부른다. `measurementId`는 설정값으로 넘길 뿐이다.
- 다른 회사 데이터와 결합하는 곳도 없다.

따라서 `NSUserTrackingUsageDescription`과 ATT 권한 요청은 필요 없다.

## 수집 데이터 표

모든 항목의 답은 같다: **사용자 신원에 연결됨 = 예**(Firebase uid로 묶인다), **추적에 사용 = 아니요**.

| Apple 분류 | 항목 | 목적 | 근거(코드) |
|---|---|---|---|
| 연락처 정보 | **이메일 주소** | 앱 기능 | Google·Apple 로그인 → Firebase Auth(`auth/googleSignIn.ts`, `auth/appleSignIn.ts`). Apple 대리 이메일 포함 |
| 연락처 정보 | **이름** | 앱 기능 | Google 프로필 이름, Apple 첫 가입 시 이름 |
| 사용자 콘텐츠 | **고객 지원** | 앱 기능 | 계정 화면의 "의견 보내기": 의견 본문과 로그인 계정의 이메일·uid를 feedback-proxy로 보내 Firestore에 저장한다(`feedback/feedbackProxyApi.ts`) |
| 사용자 콘텐츠 | **기타 사용자 콘텐츠** | 앱 기능 | ① 할 일(제목·설명·일정·반복·알림 설정) → Firestore ② AI 플랜 목표 문장 → ai-proxy → Anthropic(`aiPlan/aiProxyApi.ts`) ③ 연동 시 할 일을 구글 캘린더로 동기화(`calendarIntegration/useSyncTodosToCalendar.ts`) ④ 마감 알림: reminder-proxy가 할 일의 일정·알림 설정을 읽어 예약하고, 보낸 알림 기록(할 일 제목·마감 시각)을 저장한다(`reminder-proxy/src/store.ts`의 `history`). 알림 본문은 FCM·APNs를 거친다 |
| 식별자 | **사용자 ID** | 앱 기능 | Firebase uid. Sentry `user.id`, IAP `appAccountToken`(서버가 uid로 발급) |
| 식별자 | **기기 ID** (보수적 신고, 사용자 결정) | 앱 기능 | 마감 알림용 FCM 등록 토큰을 uid별로 reminder-proxy에 저장한다(`reminders/push/pushClient.ts` → `/push-tokens`). Apple은 푸시 토큰의 분류를 따로 정하지 않았다. 기기(앱 설치) 단위 식별자라 "기기 ID"로 신고하는 쪽을 추천한다. 빼도 심사 차단 사유가 될 가능성은 낮다 |
| 구입 항목 | **구입 내역** | 앱 기능 | 구독 상태·원거래 ID → billing-proxy가 검증 후 entitlements에 저장(`premium/iap/verifyApi.ts`) |
| 진단 | **충돌 데이터** | 앱 기능 | Sentry(`shared/lib/sentry.ts`). 운영 빌드에서만 켜짐 |
| 진단 | **기타 진단 데이터** | 앱 기능 | Sentry로 잡아 보내는 비충돌 오류(`reportError`)와 그 안의 OS·앱 버전 |

### 넣지 않은 항목과 이유

- **대략적 위치**: Sentry의 `sendDefaultPii: false` 설정 때문에 SDK는 IP를 붙이지 않는다. 그런데 Sentry 서버는 요청을 보낸 IP를 따로 저장할 수 있다. 웹 프로젝트(`tododo-client`)는 "Prevent Storing of IP Addresses"를 켰다고 기록돼 있다. 앱 프로젝트(`tododo-mobile`)도 이 설정이 켜져 있음을 사용자가 11-22에 확인했다. 그래서 라벨에 "대략적 위치"는 넣지 않는다. Firebase와 Worker의 접속 IP는 Apple FAQ상 서비스 운영에 필요한 일시 처리여서 보통 신고하지 않는다.
- **사진 또는 비디오**: Google 프로필 사진 URL은 Firebase Auth가 받는다. 하지만 기기의 사진을 가져오는 것이 아니다. 그래서 이 분류에 해당하지 않는다고 판단했다.
- **광고 데이터**: 수집하지 않는다. 기기 ID는 위 표의 푸시 토큰 때문에 보수적으로 넣었다. 그 밖에 Sentry 네이티브 크래시는 beforeSend를 거치지 않아 기기 모델이 실릴 수 있다(`sentry.ts` 주석의 "한계"). 그래도 이것은 기기 ID가 아니라 충돌 데이터의 일부다.
- **푸시 토큰**(11-26 정정): 11-23 초안은 "앱은 로컬 알림만 쓴다"였다. #233(앱 서버 푸시)부터 앱도 FCM 토큰을 서버에 등록하므로 위 표의 "기기 ID"로 옮겼다.
- **사용 데이터(제품 상호작용)**: AI 플랜 하루 사용 횟수는 KV에 2일간 저장된다(`ai-proxy/src/usage.ts`). 다만 이는 횟수 제한에만 쓰는 카운터이고 분석에는 쓰지 않는다. 그래서 넣지 않았다. 보수적으로 가려면 "제품 상호작용 — 앱 기능"을 추가한다.
- **구글 캘린더 일정**: 앱이 calendar-proxy를 거쳐 실시간으로 받아 보여 주기만 한다. 서버에 저장하지 않는다(KV에는 OAuth 토큰과 state만 있다). 구글 캘린더 OAuth 토큰은 사용자 데이터 분류에 딱 맞는 항목이 없어 넣지 않았다. 굳이 넣는다면 "기타 데이터 — 앱 기능"이다.
- **고객 지원**: 앱에도 "의견 보내기"가 있어 위 표에 "사용자 콘텐츠 → 고객 지원"으로 넣었다. 이메일·uid는 이미 연락처 정보·사용자 ID로 신고한 항목이라 새 분류는 늘지 않는다.
